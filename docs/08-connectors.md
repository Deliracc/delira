# 8 · Connectors

Connectors let the owner's own software talk to DELIRA.

## API keys

- Format: `dlr_` + 40 random URL-safe characters (30 random bytes).
- Stored as SHA-256 only, with a short prefix for display. The full key is shown once.
- Up to 5 active keys per account. Revoking is immediate.
- By default a key can: call the model API, read `GET /api/me`, and read the agent wallet (`GET /api/v1/rails/wallet`, `GET /api/v1/rails/requests/:id`).
- A key can **pay** (`POST /api/v1/rails/request`) only after the owner turns on **Can pay** for it. The owner is always notified when that happens.

## Model API (OpenAI-compatible)

```js
import OpenAI from "openai";
const client = new OpenAI({ baseURL: "https://delira.cc/api/v1", apiKey: process.env.DELIRA_API_KEY });
const r = await client.chat.completions.create({ model: "gpt-6-luna", messages: [{ role: "user", content: "Hello" }] });
```

| Route | |
|---|---|
| `GET /api/v1/models` | the models this server allows |
| `POST /api/v1/chat/completions` | streaming and non-streaming; charged like the chat (free allowance, then balance) |

The server holds the upstream provider key in its environment; it never reaches a browser or an agent. Limits apply per IP and per account (per minute, per day, concurrent, body size, output tokens), with a global daily cap.

## Notifications

Two channels, both owned by the user:

**Telegram.** The user's own bot token and chat id. The token is stored encrypted (AES-GCM).

**Webhook.** A POST to the user's own https URL:

```
POST https://your.server/hook
content-type: application/json
user-agent: DELIRA-Webhooks/1
x-delira-event: rails.waiting
x-delira-signature: sha256=<hex HMAC-SHA-256 of the raw body with your webhook secret>
```

The webhook secret is generated by DELIRA (24 random bytes) when the webhook is saved, stored encrypted, and shown to the owner in the Notifications panel.

Verify it like this:

```js
import crypto from 'node:crypto';
const ok = (raw, header, secret) => {
  const want = 'sha256=' + crypto.createHmac('sha256', secret).update(raw).digest('hex');
  return header.length === want.length && crypto.timingSafeEqual(Buffer.from(header), Buffer.from(want));
};
```

Webhook URLs are checked against server-side request forgery: https on the standard port only, no credentials in the URL, a domain name (not an IP), every resolved address must be public, and redirects are not followed.

| Event | When | Can be turned off |
|---|---|---|
| `topup.credited` | a top-up was credited | yes |
| `free.exhausted` | free messages used up (once a day) | yes |
| `balance.low` | balance below the chosen line (once until the next top-up) | yes |
| `rails.waiting` | a request waits for the owner | no |
| `rails.changed` | rails settings became looser | no |
| `rails.key` | an API key got Can pay | no |
| `rails.stopped` | a rail stopped a request | yes |
| `rails.sent` | a payment was sent | yes |
| `rails.failed` | a payment failed | yes |

## Chat tools (read-only)

`POST /api/tools/context` takes the user's message and returns live facts the chat model can cite:

- an address → native and USDT/USDC balances on the five networks;
- a transaction hash → found on whichever network has it, decoded in plain words (the method called, token transfers, approvals), with risk flags for unlimited approvals and approval-for-all;
- prices of common coins.

These tools only read. They are the same ideas as PROOF (cite a real number) and PLAIN (say what a transaction does), offered to a person in the chat.
